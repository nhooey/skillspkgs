# pkgs/

Curated per-skill flake wrappers around third-party Agent Skills hosted in upstream repositories.

Each wrapper folder is a **standalone Nix flake** that pins one upstream repo and delegates all the build/install/uninstall logic to [`nhooey/agent-skill-flake`](https://github.com/nhooey/agent-skill-flake) via `lib.mkSkillFlake` (or `lib.mkAllSkillsFlake` for [multi-skill upstreams](#multi-skill-upstreams)). Each wrapper can be consumed on its own as `?dir=pkgs/<name>`; the root flake also folds every wrapper into its package set through [`default.nix`](./default.nix).

## What this collection is for

Upstream skill projects whose authors don't ship a Nix flake themselves and won't accept a Nix-related PR. The wrapper here is the smallest possible flake that pins the upstream through its `flake.lock` and lets `agent-skill-flake` produce the install / uninstall / preview / reap apps.

## What this collection is **not** for

PRs that fall under any of these get closed:

- **First-party skill content.** Don't put a `SKILL.md` directly under `pkgs/<name>/` and ship the words in this repo. If you want to maintain skill content, ship it in its own GitHub repo or use [`nhooey/nix-skills`](https://github.com/nhooey/nix-skills); then submit a wrapper here.
- **Forks of upstream skills with local edits.** If you need to change upstream behaviour, fix it upstream or maintain a fork in your own repo and wrap *that* repo. The one exception is a small patch that removes something unsafe to install as is, such as a run-time download, described under [Patched skills](#patched-skills).
- **Skills that aren't reachable as a `fetchFromGitHub` snapshot.** If the source can't be pinned by `(owner, repo, rev, hash)`, it doesn't belong here.

## Layout

```
pkgs/
├── README.md               # this file
├── default.nix             # folds every pkgs/<name>/default.nix into the root package set
├── flake.nix, flake.lock   # standalone ?dir=pkgs face over every wrapper
├── mk-simple-vendored.nix  # shared builder for single-skill wrappers
└── <skill-name>/
    ├── default.nix         # the wrapper module; pkgs/default.nix requires it
    ├── flake.nix           # standalone ?dir=pkgs/<skill-name> face, re-exports default.nix
    └── flake.lock          # generated by `nix flake lock`
```

Every wrapper has a `default.nix`, the module the root flake and `flake.nix` both import. A single-skill wrapper's `default.nix` calls [`mk-simple-vendored.nix`](./mk-simple-vendored.nix); a multi-skill wrapper's is bespoke (see [Multi-skill upstreams](#multi-skill-upstreams)).

## What a single-skill wrapper should look like

`default.nix`:

```nix
{
  nixpkgs,
  agent-skill-flake,
  src,
}:
import ../mk-simple-vendored.nix {
  inherit nixpkgs agent-skill-flake src;
  skillName = "<skill-name>"; # must match upstream SKILL.md frontmatter `name:`
  owner = "<upstream-owner>"; # lowercased; becomes the package-key namespace
}
```

`flake.nix`:

```nix
{
  description = "<one-line description of the skill, mentioning the upstream repo>";

  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    agent-skill-flake = {
      url = "github:nhooey/agent-skill-flake";
      inputs.nixpkgs.follows = "nixpkgs";
    };
    <skill>-src = {
      url = "github:<upstream-owner>/<upstream-repo>";
      flake = false;
    };
  };

  outputs =
    {
      nixpkgs,
      agent-skill-flake,
      <skill>-src,
      ...
    }:
    {
      inherit
        (import ./default.nix {
          inherit nixpkgs agent-skill-flake;
          src = <skill>-src;
        })
        packages
        ;
    };
}
```

Then run `nix flake lock` inside the wrapper directory to generate the lockfile, and register the source in `pkgs/srcs.nix` as [Multi-skill upstreams](#multi-skill-upstreams) describes.

`mkSkillFlake` ships only `SKILL.md`, `references/`, and `scripts/` from `src`; everything else (LICENSE, README.md, the upstream's own flake.nix if any) is filtered out. If the upstream skill needs more files than that to function, this lib (and therefore this collection) is not the right tool.

## Patched skills

A single-skill wrapper can pass [`mk-simple-vendored.nix`](./mk-simple-vendored.nix) a list of `patches`, applied `-p1` inside the skill directory (`a/SKILL.md`) before it is installed. Each patch lives beside the wrapper's `default.nix`, and its header names the upstream commit it applies to and lists its edits; a bump that moves that commit has to re-check every patch. `licenseFile` ships an upstream licence kept outside the skill directory, at a path under the source root, as `LICENSE` beside `SKILL.md`. Either option keeps only the wrapper's `packages`, since mkSkillFlake's apps would install the unpatched skill. [`pstack/`](./pstack) builds two patched skills from one upstream this way.

## Multi-skill upstreams

Some upstreams ship many skills in one repo (`daymade`, `superpowers`, `trailofbits`, `caveman`, `opinionated-software-engineering`). These don't use the single-skill template above. Each gets a bespoke `pkgs/<name>/default.nix` that calls `agent-skill-flake.lib.mkAllSkillsFlake`, plus a thin `flake.nix` that re-exports its `packages` for the standalone `?dir=pkgs/<name>` face. `pkgs/superpowers/` and `pkgs/daymade/` are worked examples. The recipe:

- **Point `mkAllSkillsFlake` at the tree root and let it recurse.** `discoverSkills` descends through grouping directories and treats any directory holding a `SKILL.md` as a leaf, so a single call finds every skill — no per-suite loop. Root it at whichever directory contains the skills: `${src}/skills` for a flat `skills/<skill>/` layout, or `${src}/plugins` for a plugin-marketplace layout like `trailofbits/skills` (`plugins/<plugin>/skills/<skill>/`). When a repo ships several parallel copies of its skills, root at the most complete tree.
- **Set `source.owner` to the lowercased GitHub username.** It becomes the package-key namespace (`agent-skill-<owner>-<skill>`), so two upstreams' same-named skills don't collide. The namespace validator rejects anything outside `^[a-z0-9][a-z0-9-]*$`, so `JuliusBrussee` is passed as `juliusbrussee`.
- **Re-add referenced content the whitelist drops.** `mkAllSkillsFlake` ships only `SKILL.md`, `references/`, and `scripts/`. If a skill keeps material elsewhere — e.g. `trailofbits/skills` uses `resources/` and loose companion `.md` files — pass `extraDirs` / `extraFiles` to ship it.
- **Register the source.** Add its entry to [`srcs.nix`](./srcs.nix), and declare the `*-src` input in both the root [`flake.nix`](../flake.nix) — adding it to that file's `infrastructureInputs` list too, so it isn't mistaken for an aggregated category-2 repo — and this directory's standalone [`flake.nix`](./flake.nix). Both flakes build their `srcs` map from `srcs.nix`. `pkgs/default.nix` auto-discovers every `pkgs/<name>/` subdir and forces `srcs.<name>`, so a wrapper missing from `srcs.nix` breaks evaluation with `attribute '<name>' missing`.

## Pinning rules

- The `<skill>-src` url names only `github:<owner>/<repo>`, with no rev. The lockfile pins the commit (`rev` and `narHash`); a rev in the url as well would double-pin and make the lock a no-op.
- The same source is locked in three places: the wrapper's `flake.lock`, `pkgs/flake.lock` and the root `flake.lock`. Bump all three in the same commit, as `skillspkgs bump-vendored` does. One PR per wrapper.

## Computing the hash

`nix flake lock` does it for you the first time. To bump, run `skillspkgs bump-vendored <skill>-src` in the dev shell: it moves the root lock to the newest commit and pins `pkgs/flake.lock` and every wrapper lock that declares the source to the same rev, then lists the locks it changed for you to stage.

## Review

`/pkgs/` has no CODEOWNER, so PRs adding or bumping wrappers don't auto-request review. That's deliberate — third-party additions are open contribution territory.
